How it works

The security architecture, in detail — point by point.

The previous sections show the effect; this one shows the mechanism. Nothing is glossed over, including what remains out of reach of software alone.

A — The master key

1. Entropy generation

256 bits generated once, when the wallet is created, by the operating system's cryptographic generator (BCryptGenRandom on Windows) — never a home-made generator. This entropy is never displayed, never written down, never typed by the user, including at creation time.

2. Local device vault

The full entropy is encrypted with an OpenPGP identity specific to this device, protected by a single password. The key-derivation cost (S2K) is set to the maximum allowed by the OpenPGP format — about 350 ms per attempt on a 2011 CPU, far more on current hardware — and cannot be configured or lowered through the API used. The vault is decrypted on the fly for every sensitive operation and is never cached between two actions.

3. 2-of-3 Shamir backup kit

Generated once at creation, independent of the local vault. The entropy is split into 3 mathematical shares (Shamir secret sharing): any 2 rebuild everything, but a single share is worthless. Each share is itself encrypted with its own PGP identity and its own randomly generated passphrase, so it can be spread over 3 separate media without any of them, on its own, being a risk.

B — Derivation and signing

4. Multi-chain derivation (HD)

From the same master entropy: Ethereum and Bitcoin via BIP32/secp256k1 (m/44'/60'/0'/0/i and m/44'/0'/0'/0/i), Solana via SLIP-0010/ed25519 with a fully hardened path (m/44'/501'/i'/0'), transparent Zcash via m/44'/133'/0'/0/i and shielded Zcash (Orchard) via ZIP-32, Dogecoin via m/44'/3'/0'/0/i, Tron via m/44'/195'/0'/0/i, XRP via m/44'/144'/0'/0/i, Stellar via m/44'/148'/i' (SEP-0005), NEAR via m/44'/397'/i', Cardano via CIP-1852 (m/1852'/1815'/i', BIP32-Ed25519), Stacks via m/44'/5757'/0'/0/i, Monero following Ledger's scheme (m/44'/128'/i'/0/0). The same address is used on every Ethereum-compatible network (Arbitrum, Base, BNB Chain, Avalanche, Polygon, HyperEVM). An extra "profile" is just one more derivation index on the same entropy — the security model is the same with 1 profile or 50.

5. Building and signing transactions

Built "from scratch" for Bitcoin, Dogecoin, the Ethereum-compatible networks, Solana, Tron, XRP, Stellar, NEAR, Cardano and Stacks, without heavy SDKs such as rust-bitcoin or solana-sdk — for Dogecoin, every amount spent is also re-checked against its original transaction; Zcash uses its developers' official library (librustzcash), Monero uses monero-oxide. Deterministic nonces (RFC 6979) for ECDSA signatures, preventing private-key extraction through nonce reuse — the flaw that cost the PlayStation 3 its root key. Signatures checked internally for "low-S" normalisation by a 2,000-case test suite.

C — Active protections

6. Memory wiping

Every plaintext secret (entropy, shares, passwords) is wiped from memory as soon as it is no longer used, whatever the exit path — early return on error or panic included. Real memory locking (the equivalent of mlock/VirtualLock) also keeps these areas from being written to disk through swap.

7. Anti-brute-force lockout

A persisted failure counter triggers an increasing delay after 5 wrong attempts, doubled at each new failure and capped at 5 minutes. An internal lock prevents a script trying several passwords in parallel from losing count.

8. Address verification (EIP-55)

A mixed-case Ethereum address whose checksum does not match is rejected — the standard protection against an address copied by hand with a single character changed.

9. External link allowlist

Only the block explorers the app actually uses can be opened from the transaction history — not just a scheme check (https://), but a real list of known domains.

10. Automatic lock

After 10 minutes of inactivity on the dashboard, the app returns to the password screen — the standard hygiene expected of any wallet if someone gets physical access to the device while you are away.

D — Trust boundary

11. The frontend is never trusted

A strict CSP (connect-src 'self') stops the frontend from contacting a server directly. It never receives a secret — only public addresses, balances and transaction IDs. The permissions granted to the frontend are kept to the bare minimum (core:default only): no direct access to the file system or the network.

12. Native confirmation before every transfer

Network, recipient, amount, fees and source profile are shown in an operating-system dialog box, never an HTML modal — a compromised frontend can neither fake it nor make it silently disappear. It is followed by a 5-second delay to cancel, enforced in Rust, before anything is signed.

E — What these protections do not cover

13. Active malware on the device during use

A keylogger capturing the password as it is typed, or a direct read of the process memory at the exact moment of unlocking, bypass these protections without breaking anything. This is not a weakness specific to this project — no purely software wallet (this one or the best-known ones on the market) can fully protect against it. That is what hardware wallets are for: the key never leaves a separate device with its own confirmation screen. Saying so clearly here rather than glossing over it is part of being transparent.

What is not done yet

Code signing of the binary, an open-source release for community review, and above all a security audit by an independent professional firm — see the status above. None of the protections listed here has been validated by a third party.
